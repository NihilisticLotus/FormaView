# 版本安装与数据兼容验收要求

本文规定 Windows 安装包在版本交付前必须满足的安装、升级、降级和用户数据兼容门槛。脚本模拟、版本号伪装或安装器自身接受覆盖，均不能替代真实程序与数据的双向验收。

## v0.2 第四阶段 · 源相机与共享材质（2026-11-23）

本轮补齐 HTML 原型的源相机视图、透视/正交画幅、视锥与轨迹独立开关、框选相机与模型，以及按源材质 ID 跨网格关联/清除贴图。桌面端使用原型同一份 Camera_Material_Study.gltf 验证；原型已有对应功能，本轮未改变其设计。glTF 未提供的焦距保持“未提供”，缺省画幅跟随视口，无限远裁剪与奇异变换分别处理。同名材质不会被合并；共享网格缺少共同有效 UV 时不执行部分关联，UV 数组顺序不同时按通道名称映射。

实际截图确认了自由视图的橙色视锥、蓝色轨迹、源相机画幅留边、控制面板和共享网格列表。复查修复了两处边界：ufbx 未填 projection_axes 时采用其文档规定的 FBX 原生 +X 前向、+Y 向上；混合场景相机辅助线不再受世界坐标轴开关控制。源相机视图的画幅变化也不会使辅助线缓存状态失配。

Windows 11、Qt 6.12.0 Release、D3D11 下验证结果：

- GPU 与强制 CPU 桌面组各 7 项通过（含初始化与清理），0 失败、0 跳过。五个功能用例为 modelSourceCameraAndSharedMaterial、modelMaterialWorkflow、modelAnimationInspectorControls、modelGpuSwitchPlaybackStress、modelPanelIncubationCanBeCancelled。两组分别以 Cheering.fbx 和 RobotExpressive.glb 驱动动画回归，各执行 24 次混合模型打开。
- 新用例验证源相机投影中心、正交宽度、画幅比例、父节点动画、退出后自由取景保留、共享贴图取消/重试/清除、同名材质隔离、不同 UV 排序、文档切换复位、源文件字节不变、缺省画幅、无限远和奇异变换。
- camera_preview、model_state、model_state_uv_budget、model_render 四组 CTest 全部通过。FBX SDK 生成的实例样例验证两个网格共享同一源材质、第三个实例采用同名独立材质；FBX 正交相机和 Alembic/FBX 纯相机、混合场景均通过。model_state 中残留的旧碰撞橙色填充断言同步到既有线框契约。
- AddressSanitizer 的 camera_preview 通过，无内存错误报告；Clang UBSan trap 的 skeletal reading/pose 两组通过。UBSan 覆盖核心读取/姿态，不代表 Windows Qt 桌面端已完成全量 UBSan 检查。
- HTML 原型 camera-inspection、model-workflows、model-display、model-data 共 19 项测试通过。主程序与测试目标均成功构建。

含源相机的场景使用现有 CPU 帧构建路径，普通骨骼场景仍启用 GPU 蒙皮，GPU 日志确认 RTX 5090 D 上的实际蒙皮。验证日志与截图保存在仓库外 asset-preview-planning/development/verification/Source-Camera-Shared-Material-20261123/，最终桌面组为 camera-material-verified-gpu 和 camera-material-verified-cpu。本轮未构建或提交安装包；此记录不替代 v0.2 正式发布的安装兼容验收。

## v0.2 第四阶段 · GPU 切换复查与原型对齐（2026-11-23）

本轮处理工作区任务发布重入，以及模型替换时检查器异步创建被取消的问题。后者在 Windows 11、Qt 6.12.0、D3D11、RTX 5090 D 上取得 `QQmlIncubatorPrivate::incubate` 重复释放的现场转储。旧逻辑的受控加载回归出现两次 active 变化，且真实模型切换会销毁原检查器；修复后保留实例，关闭文件仍能取消创建。GPU 蒙皮未禁用。

原触发序列连续 30 轮通过。真实样本压力用例每轮打开 24 次，包含 Cheering FBX、Anke PSK 配对 Attack01 PSA、静态及动画 glTF，在播放中切换，并检查 GPU 几何、帧呈现和时间推进。CPU 路径独立对照；逐顶点姿态比较用例 `modelPskExternalAnimationDrive` 使用 CPU 帧，GPU 包装帧本身不保存变形后的顶点，不能直接套用该断言。

原型对齐包含 LOD 等级卡片、表面与碰撞分项、青色碰撞线框、显示或聚焦所选网格、glTF 可选 MSFT_lod 节点关联，以及外部动作的文件名与完整路径、地面网格联动。采用 HTML 原型同一 LOD 样本验证 1,068 / 332 / 156 个可见三角形。骨骼配对、glTF 动画、循环播放、模型状态、UV 预算及原生渲染六组 CTest 通过。

开发包须从已推送的 main 提交构建，保持 `0.2.0 开发测试版` 标识。打包后在应用本地 DLL 环境重新运行 GPU 连续切换与动画回归，并核对安装器载荷和源码提交。安装包、截图及转储留在仓库外。最终路径、提交号和 SHA-256 记录在对应的 `DevSetup-<commit>-20261123/delivery.json` 及安装器交付记录中。

## 每个真实版本的验收矩阵

对每个准备交付的新版本，使用该版本的实际安装包和实际程序二进制，在隔离的 Windows 测试环境中完成以下场景：

1. 从每个承诺支持的历史起点执行旧版 → 新版覆盖；从新版 → 每个承诺支持的旧版降级覆盖。覆盖沿用原安装范围和目录，不因目标版本号较低而阻止安装。
2. 每次覆盖后实际启动应用，确认已有用户设置和任务历史可读取；新增或修改设置、任务记录后重启，再确认数据仍可读取。
3. 使用隔离的代表性设置和任务数据，不接触真实用户资料；保留原始素材与已有导出文件，不让安装、迁移或卸载覆盖或删除它们。
4. 若数据格式发生变化，旧版必须继续读取兼容数据；新版独有数据必须保全。覆盖回旧版后验证兼容数据可用，再升回新版并验证新版独有数据仍可用。
5. 验收覆盖承诺支持的历史版本起点，包括跨版本直升与直降，例如实际发布的 0.1.0 与未来实际发布的 0.1.5 或 0.3.0。仅安装器样本使用这些版本字符串，不构成真实版本兼容证据。
6. 记录每个安装包与程序二进制的产品版本、来源提交/构建身份、SHA-256、安装范围、覆盖方向、应用启动及设置/任务数据读写结果。任何启动或数据兼容失败均阻断该版本发布。

版本矩阵应明确历史起点集合。某个起点若仍在支持窗口内，就必须纳入本次矩阵；不能只测相邻小版本而推断可跨版本直升或直降。测试在可还原的虚拟机快照或专用隔离环境中执行，不能把测试数据写入当前用户真实配置、任务记录、原始素材或导出目录。

### 文件类型旧图标缓存问题（2026-11-15）

用户报告：其他电脑先安装旧开发版，再用 v0.1.0 正式安装包覆盖后，已关联图片文件仍显示旧的 FormaView 图标。旧安装器将文件类型的 `DefaultIcon` 指向固定的 `{app}\\formaview.exe,0`；升级虽发送了 Shell 关联变更通知，但图标资源路径不变，Explorer 仍可能复用该路径的旧缓存图像。
